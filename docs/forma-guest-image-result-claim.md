# Dormant Guest Image result claim

This module provides an internal final consumer of the actual Guest Image copy writer's ready token and a fresh authenticated retry for an unpublished durable ready attempt. Neither entry is wired to a route, schema installer, activation flag, library, media endpoint, or UI. Calling a parser or constructing a historical receipt does not create a ready token or custody authority.

For immediate publication, the original inventory owner retains the Request, environment, database, media bucket, accounting identity, monotonic deadline and source/lease expiry. Its final publication does not start another thirty-second lifetime. It consumes ready once, proves the unchanged source and authority, prepares five personal copied bodies with native retention receipts, and constructs one candidate. The original context prefix, SAVE and result event use the same Document and Project IDs; the output and generation IDs, original creator, original payer and recorded financial/provider history remain unchanged.

The result event is `GuestImageResultClaimed`, using the exact 29-field presentation contract. Its stable seven-field claimed origin does not contain the lineage digest. The immutable full lineage binds the event's private-envelope digest, and the separate completed review binds the lineage digest. This avoids a hash cycle. No native job, grant, operation slot, result row or `GenerationCompleted` is fabricated.

For immediate publication, the writer privately retains the immutable R2 version whose complete bytes it compared with its actual upload. The final consumer permits one fresh HEAD of that same key and version before publication. That final phase cannot issue another GET or PUT, retry an uncertain physical write, or expose the retained byte proof. The media namespace is `guest-image-result-media-v1`.

`retryGuestImageResultClaim(request, env, { proof, selector })` starts a separate authenticated request using the original live guest possession proof and the closed `{ version: 1, attemptId, custodyId, manifestDigest }` selector. It requires the current personal destination principal, consent and project-author capability, the same full ready attempt and immutable intent, the original nine-column lease, and the unchanged native source. Each Request object is admitted once before the first await, including failed admission; its private seed can be consumed once. An old ready token or informational review is not accepted by this entry.

The fresh request has at most thirty seconds, conservatively capped by the original lease, source and session expiry. It never revives the old request, renews the lease, changes the original request history, or grants another physical upload. After current source proof it performs exactly one GET of the retained destination, consumes and hashes the complete saved PNG, inspects its dimensions and format, and compares exact metadata and version with one verification HEAD. It proves the source and ready row again before entering the same final consumer, which performs its own final HEAD. Thus a successful fresh retry has one GET and two HEADs, with no PUT or DELETE. Reserved, uncertain, cleanup-pending, expired and published attempts cannot enter this path.

Cleanup or a competing publication observed during verification prevents the fresh request from publishing its candidate. A completed/tombstoned selector is rejected by retry; callers must separately use the canonical result reader. There is no automatic reader redirect and no implicit retry after an uncertain mutation acknowledgement.

One D1 batch publishes N+2 canonical events, N prefix receipts, one SAVE command, five required native private-body inserts, four custody mappings, five copy mappings, the exact guest session tombstone, and the full ready-to-published attempt transition. Complete before and after predicates surround the writes. A failed assertion aborts the batch. The application mutation count is `2*N+19` (25–51 for N=3–16), excluding native event trigger effects. Native throwing-read assertions use one statement per predicate, matching the already-qualified claim-source transaction primitive.

The final database sample and native private-content receipts can differ by one millisecond because their timestamp constructions differ. Candidate construction preserves the original database-sample bounds and all five receipt times. It refuses a receipt more than one millisecond after that sample, then uses the later of the sample and actual receipt times for the single common claim time. The original expiry bound is checked again. The atomic after-proof still requires the real database time to have reached the claim time and remain before the original source, lease and body expiries; no clock, receipt or lease is rewritten.

The published-family proof materializes the complete related custody rows and tests both unchanged failing-row relations through a bounded compound query. Full-tuple exceptions, NULL handling, malformed-data checks and alias associations remain required. Qualification captures the actual final batch and compiles every distinct emitted SQL form under the existing depth, argument, binding, SQL-byte and compound-query limits.

One bounded winner inspection follows the candidate batch even when its acknowledgement is uncertain. It checks the complete recorded winner against the same immutable attempt, destination, original source and intent. It does not issue a second candidate batch or create another copy. Different tentative canonical IDs can be accepted only when the complete winner has the exact original intent and graph.

Canonical result reads are separate from the immediate publication proof. They require current destination authority, exact canonical associations, unredacted event/content rows and the recorded result-copy expiry. They do not depend on old guest possession, current payer campaign policy, or continued availability of the retired source's original private bodies. The original lease remains historical provenance; it does not become a new global revocation mechanism. Stage-body expiry is not silently promoted to the result's expiry.

The final phase reserves its finite principal, native preparation, clock, head, transaction and single winner-inspection lanes once. SQL and binding envelopes and complete D1 result/metadata envelopes are measured. Actual before/after predicate counts determine the candidate batch reservation. Existing inventory, byte and writer reservations remain spent and unchanged. No caller-supplied SQL, deadline or proof allowance is accepted.

This source allocation excludes public activation, financial changes, original provider calls, project archives, indexing and native saved-output Memory certification. It does not establish a completed generated-result customer journey until the final integrated native proof and read consumers are separately qualified.

The focused synthetic retry fixture obtains its initial reservation and ready value from the real native source and copy writer. Its primary positive aborts the original request before retry and checks the unchanged lease, single physical PUT, exact original identities and preserved payer/financial rows. Negative controls cover failed Request replay, foreign ownership and possession, source redaction, original wall expiry, genuine reserved and unknown write outcomes, changed bytes/metadata, either HEAD version change, cleanup and a competing genuine publication. Only the publication-race control deliberately keeps the original owner live. Guarded synthetic SQLite/R2 evidence is not native workerd, provider or customer-journey evidence; source review and execution receipts must state which checks actually ran.

The local native qualification covers two genuine whole-graph positives, same-invocation lost-ACK winner inspection, three transaction rollback/NULL/alias controls, and a cleanup fence winning during fresh destination verification. It does not prove two differently identified candidates racing to one winner, fresh authentication after an injected failed first publication, or every claim/cleanup serialization order. The original proposal's broader test list is preserved in the evidence, with the root's explicit decision to accept this bounded supplier on its complete atomic predicates and focused genuine failures. These unexecuted interleavings are verification limits, not passed cases. Whole customer-journey and activation acceptance remain separate.
