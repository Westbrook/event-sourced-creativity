# Dormant sponsored Slides admission and execution

This increment adds an explicit canonical-principal Slides branch to sponsor policy, approval, admission, execution and the native events POST gate. It builds on the accepted Slides contract/evidence leaf and preserves Image V1/V2, Story V4 and the separate guest V3 lane. It adds no public issuer route, schema initializer, live campaign selection, activation or provider permission.

## Exact policy and native recipe

Common policy/envelope version **5** uses family `canonical-five-slide-deck@1` and exactly one approved Slides template. The template remains version 1. Explicit payer approval covers all finite campaign, actor, window, grant-lifetime and monetary terms. Resource V1 covers existing-Document preparation/preflight/issuance and inflight limits; it does not grant initial draft storage or passive reads.

The native output is one presentation containing exactly five slides. `planning:0:initial` is followed by at most one optional `planning:0:repair`; no render call or five-call interpretation is introduced. Each full model route and its independent cost ceiling come from the actual retained quote. Initial and repair models may differ. A request has at most 121500 input and 6500 output tokens under the template, while both calls share the existing 128000-token reservation. Actual usage plus the next request maximum must fit remaining native headroom. Unused repair has no provider-call row or actual spend.

Admission uses the accepted leaf to recompute the actual registered/native release, source, retained plan/quote, routes and offline composition evidence. It matches the complete immutable envelope and live actor/payer/approval/issuance/resource authority. Native grant/slot/routes/job/holds, sponsor consumption/occupancy, resource/approval witnesses and the final native command receipt remain one atomic transaction. The original complete balanced native predicate and its source-digest guard are reused; Image and Story SQL literals retain their original bytes.

## Financial and execution boundaries

A separate source-free Slides financial branch recognizes only an original actor-owned personal `outputs` job, `render_document`, `document-render:slides` reservation pair, one original slot, exactly two allowed native stage rows and the exact immutable V5 issuance/recipe identities. The actor remains the creative owner and the sponsor remains the financial payer. Repair retains its own native model instead of inheriting the slot's initial model. The branch does not require that repair actually ran.

New paid work still requires current campaign, payer/actor, approval, issuance, resource, source, native quote and deadline proof. The events gate selects Slides only from the opaque original financial binding and requires its manual five-slide native action/settings. A caller's artifact kind or raw marker supplies no authority. The unchanged native Output hook and adapter bind the actual request string, client ID, stage, model, frozen route and caps to the durable provider-call receipt before one dispatch. Pending/uncertain evidence prevents another purchase.

The admission leaf's offline composition digest is **not** the eventual paid-wire digest: native runtime compilation adds Document identity/title and authored standing constraints. The native adapter hashes and dispatches the same actual runtime request string. No new generic request codec or fabricated future repair digest is added here.

Known original incurred costs may settle once to the original payer after live generation authority is withdrawn. Monetary proof uses original native/sponsor identities and retained call/financial receipts, not creative private bodies or current consent/configuration. A failed atomic admission rolls back its writes. Failure after a pending call or incurred usage preserves consumption/receipts, settles known usage and retains unresolved holds. Application reservations and recorded costs are not provider invoices.

Actual Slides issuer/driver composition remains a separate increment. Finite result/history/intake/PPTX materialization/download protection and original-result recovery remain required before complete sponsored Slides activation. Recovery specifically needs separate original-payer financial and actor creative authority, and must preserve the original paid correlation while fencing the recovery operation. Its existing correlation rewrite cannot be copied into sponsor settlement unchanged. These are concrete native integration dependencies; the broader automatic server-owned generation architecture remains deferred.

This change does not establish guest Slides sponsorship, live activation, subjective output quality or whole-original-plan completion. Main integration and publication remain with the coordinated deployment owner.
