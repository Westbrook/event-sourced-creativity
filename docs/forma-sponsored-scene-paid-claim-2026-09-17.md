# Sponsored Scene paid claim

This is an internal V6 adapter in the isolated native integration increment. It does not enable a public campaign, issuer, route, schema, provider call, reservation, refund, settlement or private-result read.

Ordinary Scene uses `ClaimedSceneBudget.actorUserId` for both creative custody and ledger ownership. A sponsored Scene has distinct identities, so that ordinary shape cannot describe its authorization. The new module retains the creative actor from the genuine sponsor execution seal and payer from its exact original financial seal. A private payer projection is passed only to the unchanged `claimedSceneBudgetGuard`. Audit data continues to name the creative actor and carries payer provenance in a separate field. Neither `pilot-policy.ts` nor `scene-paid-dispatch.ts` changes.

`createSponsorScenePaidClaim` accepts those two original opaque seals, the actual runtime control object and observed original claim IDs. It accepts no caller-selected payer or proof predicates. It checks the sealed Scene profile and exact financial object identity, captures a real non-aborted runtime signal, pins the control's output object, and retains the original sponsor environment/database and the four budget limit configuration values. The original Run request and cancellation lifetime remain inside the execution seal.

Every `sponsorScenePaidDispatchDeadline` invocation requires the exact prepared object and the current native dispatch handle. The native accessor checks the actual WeakMap preflight, retained receipt and current successor. The adapter compares their actor, job, scope, grant, slot, stream, correlation and native mini-app allowances with the original claim. The legacy `PreparedSceneCost.preview` has a different ordinary Scene call allowance; it supplies native custody identity, not the mini-app purchase cap.

One final read-only batch includes all current sponsor execution and original financial predicates, all native source and receipt predicates, an explicit same-slot SQL join, and the existing ledger guard. The join binds the exact job, slot, grant, reservation pair, creative actor, payer, current correlation, period, amounts and one-call native route together. Independently valid proofs for different jobs cannot be combined. The ledger guard retains its active token, executing cost, zero-used, no-refund, no-overage, current-period, counter and no-project/no-pilot conditions.

Successful receipts must be dense own-data results with integer `current === 1`. All source, campaign, quote, native job/lease and other supplied deadlines contribute to the minimum deadline. The runtime, original execution and exact native identities are checked on both sides of the owned batch await. Unknown database transport failures propagate; they are not converted into a proven zero-cost policy denial. A verification epoch prevents an earlier concurrent read from restoring success after a later verification starts or fails.

`requireSponsorScenePaidDispatchCurrent` checks the successfully verified pair synchronously after the awaited proof and immediately before provider dispatch. It catches cancellation, configuration/database replacement, native successor invalidation and deadline crossing during promise continuation. It does not replace the complete batch checks at the existing before-pending, after-pending and final provider boundaries. Starting another paid verification clears the prior continuation proof.

`sponsorScenePaidClaimIdentity` returns captured audit data after a stop without reading the database or restoring authority. Source-free accounting for known original usage stays in the existing financial path.
