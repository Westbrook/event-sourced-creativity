# Outcome Desk and protected arrangements — integrated Phase 7 boundary

The optional Desk, Canvas host, direct Store transport and protected Worker
route are integrated source behavior. This is not phase acceptance or a
release certificate. Full regression, all-nine review, native checks and
production migration gates remain separate.

## One workspace, existing authority

The Desk is a projection inside Canvas. The authoring stage remains mounted,
hidden and inert; drafts and canonical IDs stay with their original owners.
The planning-document selector remains in View. There is no first-document
or first-output fallback and no second persistent object model.

Distinct saved objects must be distinguishable before and after selection.
Only colliding visible titles gain the host's existing exact localized name;
authored titles and exact route bindings do not change. Fully composed aliases
are rechecked, with an existing encoded route key added only when the complete
names also collide. Native-target guidance focuses that exact existing run
checkbox with its contextual name; it does not change any run selection.
Completed/canceled jobs use read-only inspection wording rather than promising
ongoing progress. Their existing inspection executor is unchanged.

Recipe selection changes only URL guidance. It does not change medium,
decisions, narrative order, relationships, context membership, inputs,
approval or production workflow. Film guidance refers to actual clips or an
ordered reel, not an assembled movie.

creativeNextActions and Phase5 artifactDeliveryFor supply the exact actions:
one primary and no more than two alternatives, with saved work preceding
preparation. Other ways exposes the existing seven-format preparation choices.
Those choices open existing executors; their source, permission, quote and
paid-consent checks remain authoritative. Existing #followNextAction,
#askIntent, #useSuggestion and #createNativeBlock boundaries are preserved.

Overlay menus use native popover/popovertarget, not details/summary overlays.
Inline disclosures remain inline. Route changes and return focus belong to
the current connected host, opening, selection and exact authorized target.

## Direct transport and atomic changes

POST /api/canvas/arrangements is wired to handleCanvasArrangements; there is
no /api/canvas-arrangements alias. The controller calls
FormaStore.canvasArrangementRequest directly, never appendBatch,
syncCanvasBatch, optimistic staging or the Canvas offline queue. Existing
Phase2 authoring storage owns the exact preview and canonical receipt.

New Canvas previews reserve one actor/original-operation-derived private row
using the existing insert-only storage path. Erasing its private body does not
free that identity for a replacement. This is prospective: retained legacy
random-ID previews remain readable, but already-erased random legacy identities
cannot be reconstructed. Neither an occupied private row nor a missing row is
an applied receipt, cancellation result or permission to replace the operation.
Identity-bound storage rejects denied admission inside the existing batch,
before dependent custody/retention/cleanup/publication can change an original
row. Successful private bytes and the existing personal/scoped ownership rules
remain unchanged; no new schema, migration or identity store is introduced.

Preview binds the selected recipe, authored name, board/cards, source/layout
revisions and before/after positions, with zero providers and zero cost.
Apply requires current validation plus confirmed=true and the original
previewId/approvalHash. The server independently authorizes the whole atomic
operation; the client supplies no trusted events or clocks.

The Store forwards the existing optional controls through guardedFetch,
including its existing confirmation-modal wait. It rechecks currentness,
authorization, project and board after transport and after JSON parsing.
For a recovery-owned request, a route, opening, request, selection or source
change cannot turn a queued confirmation into a later hidden write. Preparation
uses the transport's existing dispatch notification to distinguish a pending
confirmation from an actually sent request. Reading an exact late refusal under
historical ownership does not grant a late private-plan or Apply capability.
A positive, current transport notice can separately record that a confirmation
was not approved, without dispatching this preparation attempt. It changes no
HTTP body or server protocol. Callback absence, arbitrary409, error text and
missing rows do not establish this fact; unknown dispatched work stays unknown.

## Original-operation recovery and Undo

Only the opaque operation handle is retained in the existing Canvas URL.
Close or a posture change does not cancel an in-flight save. A reopened host
resolves that exact handle before preparing anything else; no request is
automatically rebatched, replaced or applied.

Normal live reads keep their existing response contract. An explicit recovery
retrieve with includeDisposition:true may return a positively verified,
content-free expired original tuple. It permits only asking the existing
guarded resolver with action=dismiss and onlyIfUnapplied:true. An active save
remains applying and an original committed receipt wins. Only the matched
terminal outcome can finish recovery; a new Review and Apply are separate
human actions. Missing, erased, inaccessible or ambiguous evidence remains
unknown. See the [continuity contract](outcome-desk-continuity-boundary.md).

A separately witnessed source-change refusal or positive local confirmation
non-approval before free normal or inverse preparation may qualify an explicit
review of the same original choices after
a new current Check. Ordinary Close and validated same-board Desk presentation
changes may retain history, never old active permission. Each Check's rendered
corrective action belongs to that exact read; an earlier callback cannot borrow
a later qualification.
It keeps the original operation and never performs Apply, dismisses anything,
or treats mere absence as proof of unused work. A saved original still wins.
Refused Undo uses its existing inverse builder and exact original target, not
normal layout creation. Its Review and Apply remain separate human actions.

Undo reads original CanvasArrangementCreated previous_frames, applied frames
and source identity, then prepares an explicitly confirmed atomic inverse.
Current positions, dimensions, rotation, stacking and sources must match.
Protected groups and their completed inverses are filtered together in the
existing event-derived Undo ledger. Ordinary Undo/Redo keeps its own path;
saved protected layouts open review rather than generic replay.

## Integration history and verification limits

Historical R1/R2 preparation separated recipe models, the host adapter, Store
transport and backend/router wiring. Those were integration dependencies, not
remaining instructions to add another route or store. Earlier Canvas,
exact-delivery, private-source and guarded-batch overlaps were reconciled by
root-owned forwards; preserve both authorities in future changes rather than
replacing files from an intermediate overlay.

The original R2 snapshot reported 78 passing targeted cases: 17 adapter/model/
history, 30 Canvas host, 19 recipe/model and 12 backend cases, with zero
TypeScript diagnostics or external calls. These counts are historical,
overlapping preparation evidence—not current integrated acceptance totals.

Current fixtures exercise real controllers, Store/Worker code and isolated
SQLite, including personal/shared/editor scopes, capacity, original receipts,
response loss, fresh-host recovery, exact Undo and changed authority. DOM/Lit/
modal ports are not a physical browser or screen-reader certificate. Use the
phase's current gate record for terminal results and review decisions.

No fixture result establishes production approval, delivery, media quality,
spending settlement or ROI. No new provider call, financial reset, migration
workaround or release is authorized by this document. Production publication
still requires the hosting migration-runner contract and complete physical
schema/history.
