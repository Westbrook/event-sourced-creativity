# Selected-output Video exact-byte qualification

This dormant pure helper retains the default `selected-output-share-avc-mp4-v2` policy and offers the separate explicit `selected-output-share-avc-mp4-x264-163-r3060-v1` profile below. It adds no public route, source-custody witness, sharing authority, schema, UI, provider call, or permission change. Existing private Video inspection remains unchanged. Container inspection accepting descriptive metadata was appropriate for its private-reader contract; that acceptance was not an application defect.

`qualifySelectedOutputShareVideo(bytes, expected)` snapshots a native, nonshared `Uint8Array` and the exact expected SHA-256, byte length, dimensions and duration before its first await. It returns an opaque frozen result only after both this closed metadata policy and the existing native `inspectOutputAsset` pass. `copySelectedOutputShareVideoBytes(result)` returns an independent copy of the captured bytes. Serializing, spreading or forging result facts cannot recover bytes. Shared buffers, typed-array subclasses, proxies and expected-field getters refuse. An expected fact is a comparison input, not proof of ownership or permission.

The supported subset is one silent, progressive AVC video track in one nonfragmented MP4 with explicit 32-bit box lengths and one contiguous `mdat`. The version-zero movie, track and media clocks must agree through native validation and the stricter complete-timeline proof below. The optional single rate-1 edit maps the entire presentation span, without trimming or omitting samples. Track ID is 1, the next ID is 2, transforms are identity, and sample tables use 32-bit offsets. Native validation independently checks duration, dimensions against SPS, sample mapping, positive sample sizes, disjoint occupied ranges, codec configuration and NAL boundaries. The sharing policy additionally requires exact contiguous sample coverage of the entire `mdat`, matches sync-table membership to parsed IDR samples, and closes all container branches and flags. Mixed IDR/non-IDR samples refuse; an absent sync table is accepted only when every sample is IDR. No bytes can hide between boxes, in an unreferenced `mdat` region or after the container.

Supported brands are `isom`, `iso2`–`iso6`, `mp41`, `mp42` and `avc1`, with minor version 0 or 512. Fixed reserved fields and creation/modification times must be zero. The handler is a video handler with an empty name or the exact standard `VideoHandler` name. Compressor names are empty, language is unspecified, color/pixel aspect is square, and padding is at most one empty `free` box. Unknown/custom/UUID/location/text metadata, nonempty or unfamiliar `udta`/Apple item metadata, descriptive encoder names, nonempty padding, extra tracks, external references, encryption, alternate sample descriptions, large/implicit box sizes, and fragmented media refuse. The only accepted `udta` is the exact 61-byte known empty Apple wrapper, including its fixed handler and empty item list. No unknown field or nonempty item is inferred safe. These are conservative subset boundaries, not claims that every excluded feature is unsafe.

Composition timing uses an optional version-0 unsigned or version-1 signed `ctts` table with zero flags, exact length, bounded positive runs and exactly one offset per sample. Decode durations and offsets are expanded only to the existing 100,000-sample bound. Every `[decode time + offset, start + sample duration)` interval must form a unique, gapless, nonoverlapping presentation span when sorted. The single edit origin must equal that exact first presentation tick, must be nonnegative and at most one media second, and must expose the entire span; without an edit the origin is zero. The span must exactly equal the `stts`/`mdhd` duration. Movie duration is only the integer floor or ceiling of the exact cross-multiplied media duration; an integral conversion allows no one-tick trim or extension. Timing is retained byte-for-byte. This follows the distinction between decode and composition timing in [Apple's composition-offset documentation](https://developer.apple.com/documentation/quicktime-file-format/composition_offset_atom); the conservative complete-coverage restrictions are this sharing policy's own subset, not a claim that other valid edits are defective.

An optional `btrt` is a closed 12-byte numeric decoder-metadata record, using the three unsigned 32-bit fields shown by [MPEG's reference implementation](https://github.com/MPEGGroup/isobmff/blob/master/IsoLib/libisomediafile/src/BitRateAtom.c). Buffer and rate units are documented by [GPAC's media API](https://doxygen.gpac.io/v2.2.1/group__isoread__grp.html). This subset requires the declared buffer to lie between the largest sample and the complete sample payload, a positive declared average equal to the exact integer floor or ceiling of sample payload bits per media second, and maximum rate at least that average. These are consistency constraints; peak rate and complete decoder-buffer adequacy are not independently measured. Zero/unknown declared-rate forms and inconsistent estimates remain unsupported. No extra bytes or strings are permitted.

Codec configuration has one SPS and one PPS, four-byte NAL lengths, 8-bit 4:2:0 progressive baseline/main/extended/high AVC, and no scaling lists, slice groups or HRD. Supported VUI is limited to square aspect, timing and bounded bitstream restrictions; overscan/video-signal/chroma-location declarations refuse. Both parameter sets must parse through their exact RBSP stop bit with no unconsumed tail; high-profile extension data is limited to the fixed 8-bit 4:2:0 declaration with zero extension sets. The default v2 policy accepts only VCL NAL types 1 and 5 in samples, bound to the one configured PPS. In that default policy every SEI (including user-data encoder messages), filler, AUD, in-band parameter sets and other NAL types refuses. The explicit profile below permits only its one closed encoder declaration; it changes no other NAL allowance. Bounds are 24,000,000 bytes, 4,096 boxes, 100,000 samples and 200,000 sample NALs; parameter sets have a 4,096-byte bound.

This is **container metadata and byte-reachability qualification**, not complete AVC decoding or a guarantee about displayed content. Compressed picture payloads are not decoded, and the slice-prefix check does not establish that every encoded picture is displayed. Playback, visible private content, rights, covert data inside picture coding, pixel steganography, and creative quality require separate review. Exact current native custody, ordinary personal publishing authorization, approved audience/title, lifecycle consent, revocation/expiry, a token-bound asset route and actual recipient integration all remain required. No existing or future private DTO or media URL becomes publishable merely because these bytes qualify.

The helper never strips metadata, rewrites timing, transcodes, regenerates, accesses storage, or contacts a provider. Unsupported current files remain unavailable for this selected-output sharing subset; ordinary private downloads and editing are unaffected.

## Focused evidence

The focused tests derive a clean synthetic fixture from the repository's deterministic two-frame 16×16 black AVC fixture. The test-only derivation removes its known descriptive fields and SEI, preserves the actual encoded picture NALs, and rebuilds box lengths/sample offsets. The production helper does no such transformation. Native inspection and exact-byte qualification pass on that derivative; this is structural synthetic evidence, not physical-device, playback, provider or eight-journey acceptance.

The original metadata-bearing donor remains a refusal case. Tests also demonstrate that the native inspector can accept synthetic private markers in referenced SEI, appended SPS/PPS tails, or unreferenced `mdat` bytes while the stricter sharing gate refuses them. Other checks cover unknown nested boxes, nonzero descriptive fields, external/extra data boundaries, malformed tables, exact-fact mismatch, byte mutation during asynchronous inspection, detached/shared/subclass input and forged qualification handles. Historical setup failures and independent review evidence are retained in the external evidence packet, not converted into product failures.

## Version 2 compatibility increment

The original v1 commit and its sealed evidence remain unchanged in history. Version 2 adds only the exact empty metadata wrapper, validated composition/edit timing and constrained numeric bitrate forms described above. The current accepted 97-frame native Video has a gapless composition timeline and a correctly aligned nonzero edit origin; deleting its timing boxes would change playback semantics and was not attempted. Its exact bytes still do not qualify under v2: encoder SEI remains outside this metadata policy (and passing the earlier wrapper/timing stages is not acceptance of later codec fields). The original retained file was only read and its hash was unchanged. No derivative, transcode, new provider call, playback verification or repeat of its accepted live journey occurred.

Focused v2 tests retain the original 55 checks and add 39 named compatibility checks, including unsigned/signed timing, exact nontrimming edit origins, floor/ceiling movie-clock rounding, unknown/extra metadata and bitrate consistency. Independent review caught an initial inclusive one-movie-tick tolerance that accepted a 999/1001-tick movie for an exactly 1000-tick media span; the final code uses exact floor/ceiling conversion and preserves the original red evidence externally. Independent controls overlap supplier coverage and must not be added as distinct totals.

## Explicit known x264 declaration profile

`qualifySelectedOutputShareVideoWithX264Declaration(bytes, expected)` is a separate opt-in entry point. Its result has policy `selected-output-share-avc-mp4-x264-163-r3060-v1`. The existing `qualifySelectedOutputShareVideo` still uses v2 and still refuses every SEI. Both paths retain the same exact-byte capture, native inspection, byte coverage, timing, metadata, digest and opaque-byte-capability checks. Neither path activates sharing or grants permission.

The opt-in profile preserves a **declared encoder configuration**, including the encoder build, six encoding threads, two lookahead threads, and coding/rate-control settings. These are operational metadata. The declaration is self-reported: matching it does not authenticate an encoder/provider or prove that these settings produced the picture data. It establishes no assurance about visible/covert private content, creative quality, rights, current source custody or audience consent. The policy recognizes a public release identifier rather than arbitrary per-file/user identifiers.

Read-only investigation matched the local declaration against [x264's exact version writer](https://code.videolan.org/videolan/x264/-/blob/5db6aa6/encoder/set.c) and [parameter serializer](https://code.videolan.org/videolan/x264/-/blob/5db6aa6/common/base.c). The [official stable announcement](https://mailman.videolan.org/pipermail/x264-devel/2021-June/012905.html) corroborates build 163 and public commit `5db6aa6cab1b146e07b60cc1736a01f21da01154`. The vendor UUID is fixed in that writer; it is not an asset or user identifier and is not an authority token. H.264's unregistered-user-data envelope alone supplies no privacy semantics; the extra closed declaration policy is required. See [ITU-T H.264](https://www.itu.int/rec/T-REC-H.264-202408-I/en).

Only one SEI NAL is permitted, bounded to 2,048 bytes and placed before the first IDR picture in sample one. Its NAL header is exactly `0x06`; emulation-prevention handling is bounded and validated. Its RBSP must contain exactly one payload-type-5 message, the fixed x264 vendor UUID, one printable-ASCII declaration with one terminal NUL, and the exact RBSP stop byte. Foreign UUIDs, extra messages/NAL declarations, controls/Unicode, hidden tails, missing pictures and later placement refuse.

The header is the exact reviewed public tuple: x264 core 163, revision 3060, commit `5db6aa6`, the writer's fixed codec/copyright/VideoLAN wording and URL. Arbitrary hashes, private build suffixes, changed URLs and new builds refuse. The following 52 ordered fields each accept only the shown canonical literal value. This singleton configuration is usable for any otherwise-qualified clip declaring it; it is not an allowlist of one asset hash. Changes to even a legitimate setting require a separate reviewed profile.

No generic number range, free-form string, field reordering, duplicate, optional unknown field, spelling normalization, leading zero, exponent, suffix or whitespace variation is accepted. In particular, x264's serializer can emit caller-controlled `zones` text; that branch is entirely excluded, as are unreviewed custom fields and arbitrary paths. The code validates every name/value pair; it does not substitute an opaque payload hash for structural review.

This profile performs no metadata stripping, transcode or byte rewrite. A read-only check of the exact already-downloaded 97-frame native Video now qualifies under this explicit profile and returns identical bytes, while its default-v2 result remains unqualified. Its existing live-journey acceptance was not repeated. This is new pure-format compatibility evidence only: the original file hash was unchanged, with zero downloads, provider calls or public shares. Full native custody, ordinary publishing authority, consent/lifecycle, delivery routes and recipient integration remain separate requirements.

Focused tests retain the 94 v2 cases and add 83 named profile checks. These exercise every field's refusal boundary, build/UUID/grammar changes, hidden data, additional messages, placement, length bounds and immutable byte capture. The synthetic positive deliberately declares the same encoder configuration over existing synthetic picture bytes, illustrating why recognition cannot authenticate that declaration. Independent review and the exact retained-file readback are recorded separately; overlapping controls must not be summed as distinct coverage.
