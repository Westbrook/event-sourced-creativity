# Proposed exact-pair pending-settlement contract — not implemented

Recommendation: add one **opt-in supplied-pair version**, with a separately sealed `after-original-result-and-accepted-pair-exposure` mode. Keep legacy retained-source v1, supplied v2 and F3 `after-settlement-and-funded-lifecycle` behavior unchanged by default. This is needed if treatment should proceed without waiting for baseline financial finality; current code cannot do that. Optional cost-comparison reporting is already nonblocking and changing it requires no executable policy change. Immediate genuine baseline settlement could still use the existing mode, but no such authentic source is currently established. Do not make obtaining comparative costs a prerequisite to preparing this mode.

Version identities proposed for implementation: `generation-supplied-study-v3` for the supplied host descriptor, `generation-financial-policy-v2` for image-only pair advancement, and `authoring-study-v2` authority with numeric authoring proposal/receipt version2. Keep the same P2 experiment/protocol and six-stage inventory; these versions change authority/accounting, not supplied creative inputs. Reject unknown versions. `supplied()` and validator dispatch must recognize v3 explicitly. `suppliedReview()` currently invokes P4 receipt guards only for `authoring-study-v1`; v3 must require and invoke the v2 producer guard, never fall through to a less constrained legacy/fixture authority branch. Preparation financial policies remain v1.

## Authority and meaning

Extend the typed P4 proposal/compiler/display and immutable authoring receipt to bind: exact pair ID; baseline/treatment operation IDs; owner/payer/account/region and credential/header binding; both request/inventory/runtime/source/direction hashes; new contract/version; per-arm cost/token and lifecycle reservations; total independent pair exposure; explicit unknown-maximum acceptance where relevant; named lifecycle funding/retention/deletion responsibility; expiry/revocation and no-retry limits. Both per-operation policies must cross-bind the same pair descriptor and the same authoring receipt. No HTTP policy JSON, new generic grant factory, fake document or adapter endpoint.

The real acceptance must expressly permit **this one treatment while the baseline remains financially unresolved**, including both outstanding liabilities and funded custody/cleanup. Hosting Option B is not that acceptance. Estimate-mode reservations are application headroom, not a provider-enforced monetary maximum; unknown residual liability stays null/unknown and must be separately accepted. Bound-mode proof remains substantive. A finite application reserve cannot be relabeled a true price cap. Keep the genuine original-request settlement interface and financial evidence retention for eventual finality; no earlier proof of baseline finality is required solely for this mode's advancement. If there is no authentic account binding, authority issuer, accepted exposure, funded lifecycle or eventual reconciliation responsibility, the proposal stays non-committable. Identifying the responsible actor does not prove its ability to issue authoritative settlement evidence.

Do not claim P4's existing typed `verified` rows provide an authenticated registrar implementation. Reuse P4's producer and its complete display/commit, but real server-owned configuration and typed private evidence must first be issued by an identified qualified registrar under a concrete separate scope. Stage counters, optional schema or a hash do not create authority. Current classification `actual` cannot be filled using synthetic fixtures.

## Admission predicate and state machine

A separate **pair advancement** result, not `financialCompletion.nextPurchaseEligible`, must prove every item at reservation and again before each irreversible stage intent:

1. Current trusted personal actor, exact schema/runtime/configuration, unexpired unrecalled authoring receipt, review, both financial grants and exact pair-scoped mode; no stopped grant or latched hard stop.
2. Baseline is the exact first operation of this same pair/owner/grant. Original image request and response identity are durably captured; no uncertain intent, duplicate submission, changed request ID or missing usage. All advisory/exact/image/storage evidence slots are present with original hashes, complete storage stage and retained original object. Read original bytes through existing bounded custody recovery for actual human review; no provider retrieval/redispatch. Database metadata alone does not prove current object availability; an unconfirmed/missing original object stops advancement.
3. Exactly nine private evidence records, unexpired original inputs and complete capture. Human observation is immutable and matches current principal/protocol/artifact/receipt. Safety clear, fidelity pass or the prespecified expected failure, explicit resume; unknown safety/fidelity, unsafe output, changed review or stop denies. No automatic machine substitute for P2 human review.
4. Baseline may remain `hold/original_charge_unreconciled` with honest `provider_settled=0` or no final reconciliation and null uncertainty. Missing original transport/usage/custody, accounting conflict, overrun, revocation or a latched stop is not eligible. If a provisional genuine reconciliation exists, validate its binding and funding, but do not require inventing one to represent unknown finality. Never write a fake charge to enter the exception.
5. Independently accepted headroom covers baseline provider reserve **and** baseline lifecycle reserve **and** treatment provider/lifecycle reserves **and** all other recognized liabilities across periods. Token headroom likewise keeps the baseline reserve. Use `used + outstanding reserves + requested <= accepted application limit` at owner/workspace/grant levels, with no double-counting the same reservation and no use of unknown `measured_microusd` as zero. Revoked/expired funding, known overrun or inadequate capacity denies. Baseline reserves are never released/reused to fund treatment.
6. Only exact baseline reservation IDs explicitly recorded in this pair may be excluded from the *blocking predicate for this treatment*. Every unrelated/unknown reservation, document-job uncertainty, Output provider call, consequential step and preparation hold keeps current denial. The observed 17/46 inventory is a separate prerequisite and receives **no** exception.
7. At most one dispatch-capable operation for the owner. Treatment admission is an atomic irreversible lane transfer with reservation creation. Baseline remains financially outstanding, cannot execute again, and its provider intents remain immutable. No third arm, new grant, period change or different pair may evade its unresolved liability.

Do not call current `reconcile` merely to determine pair readiness: it latches a permanent supplied-pair stop for missing finality. Keep that legacy behavior. The proposed execution path checks pending eligibility independently; genuine reconciliation still settles only original immutable evidence. Already stopped packets are never rehabilitated. In the new mode, normal usable baseline capture stays `hold/original_charge_unreconciled` (current successful host capture does not call `hold()`); only this specific state may transfer. Any subsequent explicit reconciliation failure or safety/custody/dispatch failure remains terminal for advancement. No status is marked completed to free an index.

## Necessary database change

This cannot be implemented as a change to `pairGuard` and `externalGuard` alone. A narrow new schema version is required; historical optional SQL and migration files remain byte-identical. Target production had no study objects at R34, so a future fresh-install candidate should create the final new supplied schema directly, not run the old empty-fixture DROP script against live history. Legacy installations would need an independently reviewed upgrade; this recommendation authorizes none.

Proposed structure (names/types are specified in `dependencies.json`; executable DDL is next implementation work):

- Version the fresh-install `authoring_study_commits` constraint from `version=1` to the explicitly supported numeric versions1/2, with the exact authoring schema guard for this new installation. Each branch must require its matching descriptor/authority version; simply relaxing CHECK without compiler/receipt enforcement is insufficient. This is an additional narrow schema change, not an edit to historical P4 SQL. Existing authoring identity/no-update/no-delete rules remain. New proposal version2 binds pair advancement and the same seven material approval inserts; transfer state is created later only with treatment reservation.
- Add nullable `generation_study_operations.pair_yield_to`, a self-reference to the exact treatment operation, with `DEFERRABLE INITIALLY DEFERRED` foreign key and CHECK against self. Default null preserves legacy behavior. It is set only once from null on the exact baseline during a valid transfer, and never cleared/rebound. It says nothing about settlement.
- Add immutable `generation_study_pair_transfers`: primary pair ID, unique baseline and treatment operation IDs, owner/grant/plan/review/authoring-commit bindings, both policy IDs, exact request/runtime/inventory/exposure descriptor hash, baseline provider/artifact/receipt/private-evidence-set hashes, human observation binding, three baseline and three treatment reservation IDs, baseline/treatment liability/lifecycle/token amounts, accepted aggregate/headroom evidence reference, expiry and DB timestamp. Baseline FK is immediate; treatment FK is deferred until this same transaction ends. Source-free metadata only; no private financial terms. Baseline and treatment identities must differ. No caller can directly insert this row. A foreign key alone is not authority: insert guard verifies all durable joins and exact proposal/policy/observation predicates.
- Replace `generation_study_one_outstanding` **only in the new schema** with unique owner while `status!='completed' AND pair_yield_to IS NULL`. Preserve the legacy index in legacy schema. Add `generation_study_pair_operation_admission`: any pending/yielded baseline still blocks every other operation except its exact single treatment with valid transfer; completed treatment cannot let a third purchase bypass an unsettled baseline. A new row with non-null `pair_yield_to` is forbidden. Existing operation identity/other status protections remain, with a separate irreversible yield guard.
- Add fixed `generation_study_pair_eligible` view/predicate and insertion/yield guards. It encodes exact identity/grants/expiry/human/capture/funding bindings, without suppressing unknown state. Authorization is rechecked against current rows, not cached acceptance. Predicate consumers pass exact target and reservation kind; this must not be a broad owner-wide allowance.
- Amend `generation_study_external_tokens` and `generation_study_external_cost` only to admit the exact treatment token, cost and lifecycle reservation IDs while that transfer is valid. Check NEW.owner, operation/correlation/period, amount, intended operation row and grant. Other outstanding study operations still refuse. Existing baseline and treatment original settlement/no-delete triggers remain unchanged.
- Keep `generation_study_lifecycle_holds` truthful: pending baseline remains in the view when a genuine pending reconciliation exists. Amend the two lifecycle insertion triggers and host's separate `NOT EXISTS(lifecycle_holds)` admission guard to ignore **only that exact baseline for that exact treatment**, only with current funded unexpired baseline provision. An unrelated lifecycle hold, missing/mismatched funding, expired provision or overrun still refuses. `preparationGuards().holds` never receives this exception. Lifecycle settlement/closure triggers are unchanged.

One `checkedBatch` transaction must: prove eligibility/holds/headroom/authority; insert the immutable transfer; set the baseline yield pointer; insert exact treatment operation; reserve its own token/provider/lifecycle amounts using the native budget statement builders; assert all original baseline rows/holds unchanged and treatment bindings exact; commit. Deferred FKs must make half-transfer commits impossible; target D1 batch support must be proved in later focused native rehearsal, not inferred from this spec. Do not add `PRAGMA` overrides or a fallback that splits commits. Lost acknowledgement recovers the **same existing transfer and operation**, never replays intent or retries a purchase. Stage intent uniqueness remains the final dispatch lock. A rollback before commit leaves baseline/yield/transfer/reservations untouched. Race two different pair proposals for one owner: one eligible transfer at most, and any rival denied by owner lane plus operation-admission guard.

`host.mjs`'s current grant cumulative check sums `measured_microusd` and lifecycle provision; unresolved baseline measured amount can be null. New mode must replace that arithmetic with original outstanding liability/headroom accounting, including prior-period reservations. Reuse current native counter/preparation assertions, plus atomic pair aggregate checks—do not assume two preparation calls see one another's pending statements. Recheck after each inserted reservation and at final commit. Full implementation tests must cover same owner/different grants, period rollover, concurrent ordinary purchase, both arms held, a later charge overrun and lifecycle expiry.

## Lifecycle, recovery and stop

Financial truth remains separate from dispatch readiness. `financialCompletion` and genuine settlement/charge chains retain their semantics. A new mode does not set provider finality, zero uncertainty, release cost/token holds, shorten retention or close a lifecycle. Both arms can have unresolved liabilities after their one result. Existing charges/reconciliations remain immutable. Future financial reconciliation continues for both originals; no financial finality source is manufactured.

Keep purchase flags off until separate run authority. Stop prevents future stages; unknown dispatch never retries. Original artifact recovery and private evidence access require current authorization and custody. After any actual import/approval/purchase, preserve the recovery-capable release until original liabilities and cleanup obligations are settled; restoring old554 is not cleanup. Cleanup removes only exact permitted expired private content/object under the original one-attempt controls, retaining immutable source-free finance and holds. Failed deletion or metadata drift needs an exact separate recovery decision, not retries or trigger changes.

Private rehearsal/qualification indefinite retention is unchanged. It does not automatically settle the future actual-image/private-review retention contract or fund its deletion. All proposal/evidence validity must fit the retained October1 00:00UTC expiry and September30 22:00UTC mutation/recovery margin. If execution cannot fit—or the deadline is already past at implementation review—require a new explicit deadline and resealed packet as a separate future decision. Do not alter fixture clock or an expiry constant to renew authority.

## Evidence limit

`current-constraints.test.mjs` executes unchanged current SQL/guards with synthetic data and zero fetches. `proposed-contract-model.py` is a non-production acceptance sketch: it validates predicate outcomes, preserved unsettled state and an abstract atomic unique-owner claim. It is not the proposed DDL, full host integration, cross-process D1 concurrency proof, accounting verifier or run approval. The next implementation must pass these cases through the actual new schema/host/authoring pipeline, not import the model into production.
