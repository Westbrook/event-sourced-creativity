# Exact schema closure and coexistence

The full fixture baseline has 792 explicit objects; R2's 766 additional objects was a ceiling. This candidate adds **142 application objects and two controls**, retaining all 28 original N10H objects. There are 52 tables, one view and 119 explicit indexes/triggers in the resulting catalog. Automatic SQLite indexes are additional engine-managed structures.

The generator builds a full fixture **only in local memory as a source catalog**, then starts a new replica from the retained N10H migration. It seeds the exact 49 P2/P4 study-contract objects, synthetic row tables, and the original-reconciliation scope tables. It exercises the unchanged approval, execution, original recovery and stop paths against that reduced database. Missing executed table dependencies are added until the path succeeds; foreign keys, view/trigger dependencies, and canonical indexes/mandatory triggers of included tables are closed transitively. The compiled Worker subsequently exercises the complete pair and reconciliation on that exact reduced schema. No full Forma migration is packaged or installed.

The first conservative attempt inherited all feature triggers on `private_content` and budget tables. That expanded to 502 objects: memory result invalidation, consumer/asset/profile-context, resource-history and scene/nesting triggers recursively brought their feature families. These are **not required when those features are entirely absent**. The existing `nativeMemoryAnswerExclusion` code explicitly permits total additive-schema absence and rechecks the exact absence in consequential SQL; partial or malformed families fail. No qualifier was edited, schema answer emulated or canonical table renamed.

The chosen dedicated profile omits the complete optional memory, scene-source, organization-nesting and containment trigger families. The exact 305 omitted trigger names are disclosed in [closure evidence](schema-closure.json), not silently removed from an installed database. These were never in the retained N10H migration. It retains the native principal/role/consent/epoch, organization/project, private-retention, budget, original-hold, output-slot/provider-call, document-job, consequential-step, video-reconciliation/disposition, and complete P2/P4 schema dependencies that the invoked guards require. Reconciliation specifically required `project_budget_reservation_scopes` and `pilot_cost_reservation_scopes` beyond the initial execution trace.

This is a **minimum defensible canonical feature profile for these cases**, not a proof that every retained index is indispensable or that it matches production Forma. Canonical indexes and base invariants are retained rather than optimizing the schema to an artificial microbenchmark. Broader real Forma feature families need their own unchanged-guard qualification. The full table/object inventory, missing-table iterations, exact prepared SQL and dependency reasons are in schema-closure.json. Canonical DDL is in the source package's db/canonical-schema.json.

The new file is a generated **custom Drizzle migration** sourced from the canonical SQLite catalog. Default ORM reformatting cannot be substituted because P2/P4 validate exact `sqlite_schema` text. The structural snapshot is validated by drizzle-kit 0.31.10; custom triggers and exact SQL remain in db/canonical-schema.json and db/schema.ts. Run the supplied generator/metadata scripts for this unpublished candidate; once applied, append future migrations and never regenerate applied history. Do not run root Forma's ordinary migration generator or copy its 72-migration directory into this standalone package.

## Local proof and hosted preflight

The local harness applied just these two migration files to isolated emulated D1, then supplied a synthetic replica of the retained disabled tombstone. Preflight compared all explicit application/control catalog definitions; only named D1 internal bookkeeping tables `_cf_METADATA`, `_cf_KV` and `d1_migrations` are excluded from that **additional wrapper** comparison. The P2/P4 catalog guards are untouched. All 48 application fixture tables must be empty before the single atomic importer; neither control table nor the old run is a fixture grant.

Start records the full observed old tombstone hash, checks its disabled/report-null/205-import/205-cleanup state, and pins the new native owner and dataset. Cleanup rechecks the exact catalog and old tombstone hash. Local validation confirms the old row is byte-for-byte unchanged. Actual hosted row values, platform bookkeeping and applied-migration boundary must be checked later; the local replica is not a new hosted receipt.

Migration application occurs before Worker upload and may partially succeed. If deployment fails, do not rerun the old migration or reinterpret the old disabled Worker as a P5 control. Preserve the exact applied boundary, append nothing blindly, and follow the failure runbook.
