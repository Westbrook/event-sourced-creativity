## N10H: what transfers and what does not

Read-only native inspection confirms the existing retired Site `appgprj_6ab5929a74288191bf37ed429f7a7e20` remains version 1 with custom access and one `n10h_run` row in phase **disabled**, with its report removed. Its DB lists 9 tables. No importer/proof/cleanup request was sent. Historical access receipt establishes owner-private access for its original run; current metadata alone does not imply a newly authorized run.

The v35 wrapper pinned 205 chunks, accepted only fixed action fields, used a sequential guarded import cursor and a one-run proof claim, denied external fetch, checked an isolated environment, and retained a durable disabled state. v38 supplies genuine hosted D1/CPU/wall/cleanup observations. Those receipts prove that Sites supports this method without user-supplied Cloudflare IDs or an arbitrary SQL tool.

P5 is different: authenticated approval, synthetic financial state, irreversible intent, original reconciliation and R2 custody need an isolated **writer** fixture. Importing those grants into Forma's real users/budget tables would mix fixture authority with real authority. Rewriting every table name or emulating sqlite_schema to make a prefixed fixture pass exact schema guards changes the database adapter under test; it is not silent equivalence to P5's canonical DB path. A separate primitive transaction/key-prefix test is possible in shared bindings, but would not establish the full P5 managed execution invariant.

## Concrete alternative: explicitly authorize preparation on the retired private Site

This is an option, **not a target change or executable deployment proposal**. Existing Forma stays selected for the eventual image run. A successor rehearsal on the retired Site could establish managed-runtime behavior on synthetic-only application state while leaving Forma untouched, followed by separate no-purchase identity/schema/custody checks on Forma before any real run.

Deltas would be:

- Preserve the existing project, private audience, original v1 migration and `n10h_run` disabled tombstone; no original action is rerun. New source/version and a separately named P5 one-shot control record, exact synthetic import/cleanup and new expiry require approval.
- Add **R2**, currently absent. A manifest `r2` binding invokes Sites-managed resource provisioning; this is a new resource/cost delta requiring explicit approval, not a harmless rename or existing R2 proof.
- Append compatible schema-only migrations. Local comparison found all 26 shared N10H schema objects exactly identical to the current full P5 fixture schema; the two N10H control objects must remain. The full P5 fixture baseline would add 766 objects, which is an excessive unreviewed ceiling, **not** a minimal migration proposal. A targeted dependency closure/schema delta must be prepared after this alternate rehearsal target is selected; do not apply all 766 or replay the 72 Forma migrations.
- Keep the environment free of real provider keys and use synthetic response transport in the dedicated Worker. Retain source-free original fixture records/tombstone as disclosed; do not manufacture actual principal/consent/financial evidence.
- D1 writes/storage, R2 creation/put/read/delete/storage, new deployment and continuing empty-schema/source retention have unverified managed prices. Exact finite inventory, durations and cost-liability decision must accompany the eventual sealed package.
- Success would qualify that exact successor's managed methods; it would not establish Forma's actual app user, existing holds, production schema, R2 contents, effective account or live financial authority. No direct adoption follows.

No adapter for that unselected target was written, and no retired resource was mutated. It is a narrower possible future choice than creating a new Site, but it is not a way to reuse the old approval.

## Exact unavailable operation on the selected Forma target

The exposed Sites surface cannot select an isolated D1 dataset/environment for this version of Forma while keeping the ordinary Worker bound to its existing production DB, nor expose a fixture-specific environment that excludes the production provider secrets. The manifest documents one logical `d1` selection; native tools list/read that binding and manage the Site-level environment, but offer no second-binding/environment/clone control. All deploy URLs are production. The actual current target already contains real app state and configured provider secrets.

A source-level narrow wrapper can avoid passing secret properties, and R2 key fencing can limit synthetic keys, but neither isolates the canonical DB authority tables read by the unchanged P5 adapter. Removing production secrets, swapping the DB, changing all SQL/schema guards, or making arbitrary SQL endpoints is outside this request and would not establish the requested invariant. The retired Site option changes the fixture target and adds R2; it needs a separate explicit decision.

This is **a capability unavailable to the current tool/manifest surface**, not proof that Sites cannot implement it. `platform-capability-request.md` asks the platform for a supported isolated logical binding/environment or a documented equivalent. The user is not asked for a nonexistent owner record, physical IDs or direct Cloudflare credentials.
