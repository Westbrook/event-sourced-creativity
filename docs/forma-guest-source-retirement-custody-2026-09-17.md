# Original guest source cleanup after canonical adoption

Original guest source retention and canonical Project custody have separate lifetimes. A completed claim preserves the logical Project and Document IDs while creating a distinct canonical event prefix. Enrolling that canonical Project must not postpone erasure of the original guest draft and context bodies when their original deadline is due.

The earlier cleanup guard rejected every governed Project or Document with those logical IDs. A focused actual D1 run passed native enrollment, SAVE and confirmation after the separately reviewed Memory predicate repair, then demonstrated this cleanup refusal. The transaction rolled back. Its failure is preserved independently of the original custody and Memory repair evidence.

If the original conservative Project and Document guards suffice, cleanup uses that unchanged proof without consulting optional adoption state. The governed-custody exception recognizes only a proven completed v1 context adoption. It validates the complete native custody/adoption schema, immutable lineage and lease, exact original source association, and canonical prefix metadata and client receipts. The same prefix receipt is used by context-only and first-SAVE claims; original-prefix cleanup does not require a later Output state or generated result.

Each allowed Project or Document scope must belong to the receipt's destination through the exact native organization, access and Project relation. A normal synchronized Document scope has no source-event reference. The exception refuses every resource reference to an original prefix event and original guest ownership or authorship on a typed original prefix block scope. Ordinary canonical block scopes with no source-event reference remain valid. Original draft content scopes, retention scopes, event ownership and Memory exclusions remain protected.

The immutable custody proof is separate from the original private-body snapshot. It is checked before and after erasure in the same transaction and again during final read or uncertain-acknowledgement recovery. Only the original draft and committed original context prefix can be erased. Canonical copies, the separately saved guest Output tail, public events, commands and financial history are not cleanup targets.

Historical cleanup does not require a current guest login, payer approval, canonical membership or active Project status. Ordinary canonical edits and valid tombstones do not renew the original source deadline. Missing or contradictory ownership metadata refuses; erased original bytes cannot be reconstructed from a digest.

The implementation remains dormant. It adds no route, schema installer, scheduled sweep, real-data erasure, provider call or activation. Independent source and focused native/actual D1 qualification are separate delivery checkpoints. The established deployment task owns main and publication.
