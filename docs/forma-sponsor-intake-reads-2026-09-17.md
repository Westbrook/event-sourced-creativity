# Dormant Image intake reads

This increment supplies the missing pre-job read allowance for the authenticated, text-only Image intake path. Its initial base is production 383 (`36b431ea89a98e3060639fb50e0ad519468d00cb`); qualification includes the separately committed approval-proof dependency `a7403a8d2a9325bd6f837cb9ccd21300ad9980c2`. All files in this read increment are new. No existing entry, host, runtime, route, schema initializer, campaign, policy, provider or financial reservation is changed.

The original proposal requires a bounded intake allowance and controls beyond generation, including status polling and downloads (lines 457–473). The existing generated-Image read contract requires an actual job. An initial bootstrap, saved draft or intake receipt has no such job. This separate contract neither invents a job nor enlarges the previously approved generation, storage or generated-result read allocation.

## Reviewed terms and request accounting

The closed operations are `image-intake-bootstrap`, `image-intake-draft` and `image-intake-receipt`. Every operation requires explicit maximum bytes and a deadline. Explicit actor and campaign request/byte ceilings and a window are mandatory; no launch defaults exist. These limits aggregate all three operations across draft aliases and original sponsor-policy versions. The generated-result read ledger is separate: this additional allocation must be reviewed separately and is not represented as a shared all-read ceiling.

Preparation retains no business-state change; it inserts and deletes temporary assertion witnesses in one transaction. Approval requires an actual bounded, typed POST from the original authenticated payer, the exact reviewed terms digest, the explicit approval confirmation, and the full immutable original sponsor approval. An admin role, actor-supplied payer, isolated digest or forged policy row does not provision read authority. Approval and the new read policy are stored atomically. All schema arrays remain dormant exports.

Each actual request reserves a fresh UUID and its entire operation byte limit. The database clock supplies admission, deadline and charge-through times. Failed work, cancelled requests, aliases, repeated status checks and lost acknowledgements do not refund or reuse this reservation. The same campaign/actor keys retain aggregate usage across intent, draft, request and policy changes. An opaque ticket is bound to its exact Request, environment, database, authority, canonical resource and operation and can resolve once. The three new tables use `WITHOUT ROWID`, so an implicit-row-ID replacement cannot evade their immutable logical-key guards.

## Current custody and original recovery

A fresh bootstrap accepts only a server-selected campaign through the internal API, then requires its current approved canonical-principal Image authority and registered release. Future public entry configuration must select that campaign; browser query parameters cannot supply financial authority. This descriptor starts no model work and grants no generation permission.

Draft-ID and intent-ID aliases resolve the same immutable original intake/resource receipt before any private draft or canonical event payload is read. The saved receipt selects the original campaign and policy, independently of today's entry configuration. Saved bootstrap, draft and native receipt reads preserve current principal, personal custody, retention, redaction and removal checks. They do not depend on the old session snapshot, remaining generation entitlement, current campaign enablement or generation expiry. Generation revocation is not creative erasure.

After reservation, the resolver calls the actual native draft reader and the actual native intake receipt checker. It preserves the original hash-covered sponsor marker, plan, release, event identities and receipt. It does not reconstruct a fictional ordinary plan or infer `OutputPlanConfirmed` from a created Document. Pending native receipts remain pending.

A finite read-only database adapter accepts the qualified native read shapes only. SQLite measures the complete selected row JSON and row count before returning private bytes to the Worker; it projects only those approved columns. The resolver counts those actual retained bytes plus its emitted JSON body under the same budget. It uses an absolute monotonic cutoff together with the stored database deadline; delayed awaits cannot restart the allowance. Full lineage, current authority, exact private body and exact native receipt-row proofs are checked before disclosure, including the exact database capability after the final await. Unknown query shapes, oversized data, expired work and changed custody refuse disclosure. The allowance measures retained row JSON and response bytes, not physical database storage, database scan work, HTTP headers or existing principal/access-policy metadata read before admission.

## Integration still required

No registered HTTP or queue path calls these modules or installs their schema. These internal APIs do not make the sponsor client reachable or protect existing public aliases. The next integration must reserve the exact entry/host/index/intake paths with their owners, provide a closed trusted entry configuration, and route every relevant bootstrap and draft/receipt alias through this complete composition. It must retain ordinary intake behavior and ordinary authenticated result custody, preserve the original sponsor campaign on resume, and avoid enabling ordinary output controls or background job driving for sponsored Documents.

That integration also needs an approved operational response to these immutable read allocations: this increment has no mutable renewal, revocation or reset API. Changing a policy cannot reset usage. Actual payer, audience and allowance values and any public activation require applicable approval. Anonymous onboarding, uploads, references, parsing, other seven outputs, generated result/media/download routes, and a reusable public campaign platform are outside this Image intake increment.

## Qualification

The accompanying tests provision only synthetic policies in disposable SQLite using the actual authenticated payer approval and native initial intake/commit functions. No network/provider call, production database write, real policy, financial hold or audience change is permitted. Final evidence records the selected cases and source hashes separately.

An attempted simplification of the new native receipt guard was rejected by automatic approval review because replacing the composed custody/lineage/ticket proof with only the retained-draft guard could weaken authorization. That edit was not applied. The complete composed guard remains in the implementation; no workaround or alternative weakened guard was used.

Subsequent deployment-limit evidence required a distinct, reviewed repair. The complete ticket assertion already contains every frozen authority, actor, custody and lineage assertion, plus the payer-approved read policy and immutable attempt/deadline. The resolver retains that whole conjunction once, instead of adding the identical authority subset a second time. It still adds the exact draft-body proof, native receipt-row proof and final database deadline. This duplicate-only factoring preserves all predicates. A bounded parameter packer and null-preserving JSON chunks fit the [published D1 query limits](https://developers.cloudflare.com/d1/platform/limits/); exact pre-fix failures and post-fix metrics are retained with the qualification packet.

The strict engine exercise also exposed expression-depth failures that ordinary SQLite's larger default limit did not reveal. Independent probes establish depth 100 in bundled local workerd/D1 and reproduce the original failing statements. The shared campaign approval proof was repaired and committed separately. This read layer represents its complete debit, ticket and final disclosure predicates as materialized zero/one-row gates in each original atomic statement. False or NULL predicates still refuse; no earlier successful read substitutes for a current proof.

For native receipts, the adapter first recognizes the exact full native SELECT, full supplied guard and complete ordered binding vector. It then moves all seven complete predicates into mandatory joined gates in that same SELECT, retaining the native LEFT JOINs, ordering and row/byte bounds. The actual native commit API still receives its original full guard. The frozen definitions and bindings also travel with the exact returned-row comparison into the final disclosure statement. Unknown future SQL or changed bindings fail closed. This is finite statement construction for the current Image intake reader, not a general SQL proxy.

Fresh bootstrap, saved draft, unconfirmed receipt and completed receipt pass the actual SQLite compiler with depth 100, function arity 32, 100 parameters and 100,000 SQL bytes. Independently, all four complete internal read functions pass against actual local workerd/D1 databases seeded from the real synthetic native fixtures: original status/bodies match, each request retains one full-byte allocation, and all other application/financial tables remain unchanged. The largest observed statement is 73,087 bytes; the largest binding vector has 69 values. The application functions run in Node with an actual local D1 backend; this does not qualify a deployed Worker, public HTTP path or native intake write on D1. Historical product failures, reviewer harness setup errors, equivalence probes and final source versions remain distinct in the evidence packet.
