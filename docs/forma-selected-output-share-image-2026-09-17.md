# Exact PNG qualification for selected-output sharing

This source-only prerequisite does not enable sharing. It adds no route, schema, authority policy activation, provider call, upload, public audience or changes to ordinary downloads/editing. Current custody and deliberate publishing authority remain separate requirements.

`qualifySelectedOutputShareImage(bytes, expectedFacts)` copies a native, nonshared `Uint8Array` before awaiting work and checks an exact expected SHA-256, byte length, width and height. Expected facts are closed data fields, not getters. The result uses policy `selected-output-share-png-v1`. Qualified source bytes remain private to a WeakMap; `copySelectedOutputShareImageBytes(result)` returns a fresh copy. Serialized or forged facts cannot recover bytes. Retaining the in-memory qualification keeps one bounded byte snapshot alive until garbage collection.

The initial supported subset is noninterlaced, 8-bit RGB/RGBA PNG. It accepts IHDR, contiguous IDAT and final IEND, optional sRGB intent 0–3, standard gAMA 45455, exact standard sRGB cHRM values, and one validated RGB transparent-color tRNS. Optional rendering chunks must precede image data and cannot repeat. This includes the clean original/current-edit synthetic PNG formats already exercised by native Image tests. It does not establish coverage of every provider-produced PNG.

All other chunks refuse, including text, EXIF, ICC profiles, suggested palettes, timestamps, physical-resolution metadata, animation, and unknown extensions. Grayscale, indexed-color, 16-bit, interlaced and non-PNG files also refuse in this increment. This is a conservative supported subset; rejected metadata is not necessarily malicious. No metadata is stripped and no image is transcoded or replaced. A later policy may explicitly qualify additional structures through separate review.

The independently selected `qualifyResolutionSelectedOutputShareImage(bytes, expectedFacts)` uses policy `selected-output-share-png-resolution-v1`, including for clean v1 PNGs. It has the same captured bytes, trusted expected facts and copy API. The existing qualifier and default generic result types remain `selected-output-share-png-v1`; calling it still refuses each resolution chunk. There is no caller-supplied policy string or automatic fallback.

The resolution profile adds only one optional, complete, contiguous `eXIf`, `oFFs`, `pHYs` trio, in that order before IDAT, with no duplicates. The 54-byte eXIf payload must be the full big-endian TIFF layout: byte order `MM`, marker 42, first IFD offset 24, two rational values 72/1 at offsets 8 and 16, exactly two IFD entries (XResolution 0x011a and YResolution 0x011b, type RATIONAL 5, count 1, offsets 8 and 16), and a zero next-IFD pointer at offset 50. Every payload byte is checked; there is no ResolutionUnit tag and this profile does not infer an inch unit from the rational values. Alternative encodings, equivalent but different rationals, other tags, nested IFDs, EXIF prefixes, padding and trailing data refuse. The 9-byte oFFs must contain zero signed x/y offsets and pixel unit 0. The 9-byte pHYs must contain 2834 pixels per metre on both axes and metre unit 1. These finite resolution constants are independent of asset identity or content hashes.

The structural meanings follow [PNG Third Edition §§5.6, 11.3.4.3 and 11.3.4.5](https://www.w3.org/TR/2025/REC-png-3-20250624/), [registered PNG extensions §§2 and 3.1](https://www.libpng.org/pub/png/spec/1.1/pngext-1.1.0-pdg.html), and the TIFF/Exif field definitions in [CIPA's accessible 2019 English draft §§4.6.2 and 4.6.4](https://www.cipa.jp/std/documents/e/DC-X008-Translation-2019-E.pdf). The latter is a draft, not the final Exif 2.32 publication. The gate checks this finite byte layout; it claims neither general Exif conformance nor actual display/print density. Contiguity and all-three presence are deliberately narrower profile requirements than PNG's independent optional chunks.

This explicit profile addresses the locally observed resolution-only metadata in an embedded GLB PNG texture. It does not qualify the separate Image/Storyboard `caBX` C2PA provenance, arbitrary EXIF, private identifiers, opaque profiles or unknown ancillary fields. No C2PA assertion is stripped and no provenance is rewritten. Actual-file compatibility, current custody, final share authority and audience acceptance remain separate evidence; passing authored fixtures alone does not establish them.

The gate reuses `inspectOutputAsset` for exact digest, format, CRC, zlib/scanline validation, dimensions and expansion limits. Its additional parsing is bounded by the existing 24,000,000-byte native asset limit and 4,096 chunks; native expanded image data is bounded by 32 MiB. Known color fields receive closed value/length checks so they cannot become uninspected string/profile containers. The gate does not claim image-content review, rights, steganography detection, or a guarantee that selected pixels contain no private information.

The focused tests use local authored PNG fixtures only. They preserve the demonstrated boundary that an ordinary private PNG inspector accepts a tEXt chunk while this sharing prerequisite refuses it. Checks cover exact original/edit bytes, RGB transparency and rendering fields, mutation isolation, forged result refusal, hostile input descriptors, hash/dimension/length substitution, disallowed metadata, native malformed-data checks, trailing compressed payload and finite limits.

Additional resolution-profile tests change each of the 72 metadata payload bytes independently, reject short/long payloads and hidden tails, partial/reordered/interrupted/duplicated trios, post-IDAT chunks, alternative TIFF encodings and nested pointers, and preserve native validation and capture/fact boundaries. The original v1 cases remain in the same suite.

Next integration must extract/reuse the current native Image custody witness after its active read-hook change freezes, bind the original completed job and current edit to an ordinary-personal publishing witness, and connect this gate to reviewed prepare/commit plus token-scoped media delivery. The text sharing contract is unchanged. Sponsor, guest, shared-project publishing policy and actual audience expansion are not authorized by this helper.
