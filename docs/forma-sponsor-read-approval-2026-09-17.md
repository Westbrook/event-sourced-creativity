# Dormant Image read-policy approval

This increment supplies trusted preparation and one-time provisioning for the immutable Image read-policy row already consumed by the sponsor read ledger. It adds no public route, schema initializer, actual payer, policy values, enabled campaign, financial hold, generation call or sharing permission. The application remains unactivated for this flow.

`prepareSponsorReadApproval` and `approveSponsorReadPolicy` both use the existing native canonical-principal reader. The caller must be the original payer, with the original campaign's captured payer authority still current. A campaign issuer or unrelated administrator cannot approve for the payer. The existing `sponsorApprovalAssertion` remains the source of campaign authority; the recorded original issuer is only a witness to that existing approval and is never impersonated. Current email and linked or unlinked active pilot membership are repeated in the final transaction.

Preparation requires an explicit POST with the original campaign ID, original sponsor-policy digest and every closed `SponsorReadPolicyV1` limit. It returns review terms covering that proposal, original approval ID, original terms digest and payer. The digest grants no capability. Commit freshly authenticates and verifies the full original canonical approval command, then requires `APPROVE_SPONSOR_READ_POLICY` and the exact reviewed terms digest.

An active, unexpired original campaign is required at preparation and provisioning, including command replay. Provisioning must therefore precede newly offered sponsored work. Once provisioned, completed retained-owner reads consume the stored policy independently of generation expiry, exhaustion or revocation, subject to current custody and read quotas. Command replay is not a prerequisite for those reads.

The commit uses the existing native atomic-assertion mechanism. Original campaign, approval, payer snapshot, email and pilot membership proofs run inside the same transaction as the policy and new immutable provenance row. A final join proves both exact rows. Failures roll back both; simultaneous exact calls and lost acknowledgments recover the one original. Conflicting terms or approval IDs cannot replace it. Replay does not reset read attempts, change generation authority, settle costs or credit usage.

All four original JSON cells are checked for SQLite TEXT affinity, bounded UTF-8 BLOB byte length and embedded NUL before returning them. Limits are 128 KiB for original reviewed terms, approval command and captured payer authority, and 256 KiB for the derived policy. Oversized or malformed original records fail closed. The existing native original-approval predicate verifies the captured principal snapshot; the new module does not add a financial authority model.

The existing five-column `experience_sponsor_read_policies` schema is unchanged. The separate `SPONSOR_READ_APPROVAL_SCHEMA` is exported dormant SQL only. A future reviewed activation must install both this provenance schema and the existing policy/attempt schemas, the exact native read-lookup index definitions supplied by the read-hook integration, and all necessary hooks for the operations actually offered. No initializer imports these schemas here. Missing lookup indexes and historical distinct-payer Image ownership inconsistencies must remain closed; ordinary access is not an escape path for sponsored lineage.

Qualification uses disposable real SQLite and synthetic native principals. Forty-two focused cases cover payer identity, exact review, immutable original campaign binding, malformed/oversized command and stored data, stale email/authority/policy/pilot races, transactional rollback, duplicate/conflicting commits, lost acknowledgments, and a provisioned completed result read after generation revocation and expired grants. The completed-result fixture uses the existing in-memory provider responder; no live provider is called. A separate unbounded-column mutation fails all twelve stored-data tests, demonstrating that the SQLite boundary checks are meaningful. Historical runs and independent review are retained in the delivery evidence.

Actual payer/account, audience and resource values remain user decisions. This source increment does not satisfy browser acceptance or authorize launch. Remaining native aliases and public activation are tracked separately by the integration owner.
